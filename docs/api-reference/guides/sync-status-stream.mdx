## Overview

The sync status API lets you observe the entire lifecycle of every sync that runs for a user — across pulls, webhooks, SDK uploads, Apple Health XML imports, and historical Garmin backfills — in real time.

Three endpoints are exposed:

- **`GET /api/v1/users/{user_id}/sync/stream`** — long-lived [Server-Sent Events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events) connection that streams every event as it happens.
- **`GET /api/v1/users/{user_id}/sync/recent`** — the last N events buffered in Redis (default 50, max 200, retained for 72 hours).
- **`GET /api/v1/users/{user_id}/sync/runs`** — the latest event per run (one row per `run_id`), so you can quickly inspect which syncs are in progress and how recent ones ended.

All three accept the same `ApiKeyDep` authentication as the rest of the public API: pass your API key via the `X-API-Key` header.

<CodeGroup>
```bash X-API-Key
curl -H "X-API-Key: YOUR_API_KEY" \
  "https://api.openwearables.io/api/v1/users/USER_ID/sync/stream"
```
</CodeGroup>

**HTTP status codes (all three endpoints)**

| Code | Meaning |
| ---- | ------- |
| `200` | Success |
| `401` | Missing or invalid API key |
| `404` | User not found |
| `422` | Validation error (invalid parameter value) |
| `500` | Internal server error |

**Error response shape**

```json
{ "detail": "User not found" }
```

<Note>
The SSE endpoint also supports webhooks — if you have outgoing webhook endpoints registered, terminal sync events (`sync.completed`, `sync.failed`, `sync.cancelled`) are also dispatched as Svix webhooks. See the [Webhooks guide](/api-reference/guides/webhooks).
</Note>

## Saved Data Inspection

The dashboard's **View data** button loads current processed measurements and events from PostgreSQL only when opened. Sync list requests do not load record bodies. Pages contain at most 100 records. Fresh pages are cached in the browser for 30 seconds.

`GET /api/v1/users/{user_id}/sync/runs/{run_id}/saved-data?limit=100` returns `user_id`, `run_id`, `provider`, `scope: "user_provider"`, `records`, and `next_cursor`. Pass the opaque `next_cursor` as `cursor` for the next page. Records use stable type/UUID order, not time order. The endpoint reads the run's user and provider from retained sync metadata and filters database records by both. It never counts all records. Authentication matches the sync endpoints. Invalid cursors return `400`; missing or mismatched users/runs return `404`.

**These records are not linked to individual sync runs.** They are current saved data for the selected user and provider, not original input or an immutable run snapshot. Measurements include their series type ID, value and recorded time. Events include category, start/end time and duration. Detailed workout/sleep payloads and archived measurements are not included. Updated or deleted records can change between pages. A run must still exist in Redis to resolve its provider.

## Received Data Inspection

Received data is captured at ingestion time, never reconstructed from current database rows. Existing runs are not retroactively captured. Bodies are not included in run lists or SSE messages.

- `GET /api/v1/users/{user_id}/sync/runs/{run_id}/received-data?limit=20&cursor=0` lists artifact metadata. `limit` accepts 1-100; `cursor` is the next cursor returned by the previous response.
- `GET /api/v1/users/{user_id}/sync/runs/{run_id}/received-data/{artifact_id}?limit=100&cursor=0` returns a bounded preview. `limit` accepts 1-100 JSON records. A dictionary is one record. Previews exceeding 256 KiB fall back to a truncated 16,000-character text preview.

Both endpoints accept a developer bearer JWT or `X-Open-Wearables-API-Key`, using the existing developer/admin API policy. No arbitrary object keys or storage URLs are accepted or returned. There is no additional endpoint-specific rate limit; apply your deployment's API rate limits.

```bash
curl --fail-with-body \
  -H "X-Open-Wearables-API-Key: $OPEN_WEARABLES_API_KEY" \
  "$API_BASE/api/v1/users/$USER_ID/sync/runs/$RUN_ID/received-data?limit=20"
```

The list response contains `run_id`, `user_id`, nullable `expires_at`, `capture_status`, `artifacts`, and nullable `next_cursor`. Artifacts contain `artifact_id`, `captured_at`, `expires_at`, `representation`, `kind`, `content_type`, `size_bytes`, `status`, and `label`. Preview responses contain `artifact_id`, `representation`, `content_type`, `size_bytes`, and `preview` (`format`, nullable `records`, nullable `text`, `truncated`, nullable `next_cursor`).

```json
{
  "run_id": "pull_4189248b416143fe",
  "user_id": "f7512100-c535-45e7-9e49-e19d456b5ab9",
  "expires_at": null,
  "capture_status": "unavailable",
  "artifacts": [],
  "next_cursor": null
}
```

Capture states are `available`, `partial` (some oversized/failed/missing artifacts), `not_captured` (no snapshot), `expired`, and `unavailable` (storage unconfigured or inaccessible). Artifact states are `available`, `oversized`, `failed`, and `expired`. HTTP errors: `400` invalid pagination, `401`/`403` authentication, `404` user/run/artifact mismatch, `410` known expired artifact, `503` unreadable artifact. Handle unavailable states without treating them as empty received data. Successful empty/unconfigured lists return `200`.

### Source Coverage And Limits

- SDK (Apple, Samsung, Google): normalized JSON batch received by the import worker, before processing. This is not the original HTTP wire body.
- Pull, historical REST backfill, and linked-account pull: provider JSON responses through the shared authenticated API client; supplementary legacy raw-response hooks cover provider-specific clients. Linked users get independent scopes.
- Webhooks (Oura, Whoop, Polar, Strava, Suunto): normalized notification body after provider resolves the target user; bounded fetched-response snapshots (up to 20 responses, 10 MiB aggregate buffered bytes) are attached to that resolved user's run. Count/byte buffer overflow and serialization failures mark the affected user's capture `partial`, including when all fetched bodies were dropped; no individual dropped-artifact metadata is retained. User-unresolved failures have no attributable artifact.
- Garmin wellness/activity webhooks: only the resolved user's notifications are captured, never the entire multi-user batch. Notifications are also attached to active Garmin backfill runs. Linked profiles have independent indexes and object paths.
- XML import: original XML bytes, with metadata-only binary preview. FIT downloads through the shared binary client during an active scoped run: original FIT bytes with metadata-only binary preview. XML/FIT are not downloadable through this API.

JSON is explicitly labeled `normalized`: known authentication fields and HTTP URLs are redacted recursively. XML/FIT retain original bytes privately and are never echoed as text. Maximum stored artifact size is 10 MiB; larger artifacts retain `oversized` metadata. Up to 1,000 artifacts per run are atomically reserved, including interrupted writers; overflow is `partial`. Identical content of the same kind is deduplicated. Response order is artifact-ID order; pagination during active ingestion is not a transactional snapshot. Capture is best effort: worker/Redis/storage failure can cause missing data; it never blocks sync success.

### Deployment And Retention

Capture bodies use the existing PostgreSQL database. Redis holds capture metadata. No S3 bucket, AWS credentials, or new environment variables are required for this viewer. Apply database migrations before deploying API and Celery processes. API and all workers must use the same database and Redis. Keep Celery Beat running for scheduled deletion. `RAW_PAYLOAD_STORAGE` controls separate debug copies only; it can remain `disabled`. Existing S3 captures are not migrated, and old runs without PostgreSQL bodies cannot be reconstructed.

A publisher-stamped Celery header (`received_capture_created_at`) fixes the original task age and is preserved across retries. Captures older than 72 hours are rejected even after metadata eviction. Already-queued legacy tasks without this immutable header fail closed (no capture); deploy/restart API and all publishers before expecting new captures. Direct synchronous calls use their initial capture time. The first capture atomically fixes run expiry from that original age; every list/preview checks absolute expiry. Expiry markers are bounded to ten days, metadata to seven days after body expiry; no permanent keys are created. Use durable non-evicting Redis for complete history.

Atomic Lua admission enforces the 1,000-slot cap. Per-artifact 60-second ownership leases permit retry of failed or interrupted writes without extending original expiry; fencing prevents stale writers publishing metadata or releasing a successor's lease. A PostgreSQL primary key and `ON CONFLICT DO NOTHING` make recovery after a committed body write safe without overwriting the immutable body or extending its expiry. Body writes use independent transactions. On write failure metadata stays failed and a later delivery can retry. Existing event histories are retained for 72 hours, capped at 200 recent events per user.

**Read expiry is not physical deletion.** The API and body repository deny reads at 72 hours. An hourly Celery task deletes up to 10,000 expired bodies in batches of 100. Locked rows are skipped so overlapping cleanup tasks can progress safely. Cleanup delays or backlogs can retain expired bodies longer. Database backups have separate retention and access policies. Existing S3 debug copies and legacy capture objects have separate retention and are not deleted by this task. Monitor cleanup, database size, database access, and Redis durability.

## Event Schema

Every event is a JSON object emitted as the `data` field of an SSE message with `event: sync.status`:

```json
{
  "event_id": "evt_01HZ...",
  "run_id": "pull_garmin_user42_1730000000",
  "user_id": "user42",
  "provider": "garmin",
  "source": "pull",
  "stage": "fetching",
  "status": "in_progress",
  "message": "Fetching workouts",
  "progress": 0.42,
  "items_processed": 21,
  "items_total": 50,
  "error": null,
  "metadata": {},
  "started_at": "2024-10-27T10:15:00Z",
  "ended_at": null,
  "timestamp": "2024-10-27T10:15:32Z"
}
```

### Fields

| Field             | Type                  | Description                                                                                                          |
| ----------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `run_id`          | `string`              | Unique identifier per sync run. Multiple events share a `run_id` as a sync progresses.                               |
| `provider`        | `string`              | Lower-case provider slug (e.g. `garmin`, `oura`, `apple`).                                                           |
| `source`          | `SyncSource`          | One of `pull`, `webhook`, `sdk`, `backfill`, `xml_import`.                                                           |
| `stage`           | `SyncStage`           | One of `queued`, `started`, `fetching`, `processing`, `saving`, `completed`, `failed`, `cancelled`.                  |
| `status`          | `SyncStatus`          | One of `in_progress`, `success`, `partial`, `failed`, `cancelled`. Terminal statuses end a run.                      |
| `progress`        | `number \| null`      | Optional 0..1 fraction. Not all syncs report this.                                                                   |
| `items_processed` | `number \| null`      | Optional count of items processed so far.                                                                            |
| `items_total`     | `number \| null`      | Optional total when known.                                                                                           |
| `started_at`      | `string \| null`      | ISO-8601 timestamp when the run started.                                                                             |
| `ended_at`        | `string \| null`      | ISO-8601 timestamp when the run reached a terminal status.                                                           |
| `timestamp`       | `string`              | ISO-8601 timestamp of this individual event.                                                                         |

## Streaming endpoint

```bash
curl -N "https://api.openwearables.io/api/v1/users/USER_ID/sync/stream?replay=20" \
  -H "X-API-Key: YOUR_API_KEY"
```

**Path parameters**

| Parameter | Type | Required | Description |
| --------- | ---- | -------- | ----------- |
| `user_id` | `string (UUID)` | Required | The user whose sync events to stream. |

**Query parameters**

| Parameter | Type | Default | Range | Description |
| --------- | ---- | ------- | ----- | ----------- |
| `replay` | `integer` | `20` | `1..200` | Number of recent events to replay before the live stream begins. Allows a freshly connected client to catch up on in-progress syncs. |

The `replay` parameter causes the most recent events from the last 24 hours to be replayed before the live stream begins, so a freshly connected client can see in-progress syncs immediately.

The stream emits:

- A connect comment (`: connected`) when the connection is established.
- One SSE message per event (`event: sync.status`, `data: <json>`).
- A `: heartbeat` comment every 15 seconds to keep the connection alive.

Browsers can consume the stream using `EventSource` (without auth headers) or `fetch` + `ReadableStream` (with a `Bearer` JWT token in the `Authorization` header). Both authentication methods are accepted by the same endpoint — no separate dashboard variant is needed.

**Example SSE stream output**

```
: connected

event: sync.status
data: {"event_id":"evt_01HZ...","run_id":"pull_garmin_user42_1730000000","provider":"garmin","stage":"fetching","status":"in_progress","progress":0.42,...}

: heartbeat

event: sync.status
data: {"event_id":"evt_01HZ...","run_id":"pull_garmin_user42_1730000000","provider":"garmin","stage":"completed","status":"success","progress":1.0,"ended_at":"2024-10-27T10:16:45Z",...}
```

**Error responses**

```json
HTTP/1.1 401 Unauthorized
{ "detail": "Invalid authentication credentials" }
```

```json
HTTP/1.1 404 Not Found
{ "detail": "User not found" }
```

### Example: Node.js

```javascript
import { EventSource } from 'eventsource';

const url =
  'https://api.openwearables.io/api/v1/users/USER_ID/sync/stream?replay=20';
const es = new EventSource(url, {
  fetch: (input, init) =>
    fetch(input, { ...init, headers: { ...init.headers, 'X-API-Key': KEY } }),
});

es.addEventListener('sync.status', (msg) => {
  const event = JSON.parse(msg.data);
  console.log(`[${event.provider}] ${event.stage} - ${event.status}`);
});
```

```bash
curl "https://api.openwearables.io/api/v1/users/USER_ID/sync/runs?limit=20" \
```


**Path parameters**

| Parameter | Type | Required | Description |
| --------- | ---- | -------- | ----------- |
| `user_id` | `string (UUID)` | Required | The user whose run summaries to return. |

**Query parameters**

| Parameter | Type | Default | Range | Description |
| --------- | ---- | ------- | ----- | ----------- |
| `limit` | `integer` | `20` | `1..50` | Maximum number of run summaries to return. |

Returns the **latest** event for each unique `run_id` from the past 24 hours (one row per run), ordered newest first. ## Rate limiting

The sync status endpoints share the global API rate limit. The SSE stream endpoint (`/sync/stream`) holds a single long-lived connection per client — there is no per-user connection cap, but you should maintain **at most one open stream per user** and reuse it rather than opening a new one on each page load.

For polling-based fallbacks using `/sync/recent` or `/sync/runs`, a reasonable poll interval is **5–15 seconds**. Polling faster than once per second provides no meaningful benefit since event latency is already sub-second via the SSE stream.

**Retry guidance**

If the SSE stream disconnects (network error, server restart, or a `5xx` response), implement exponential back-off before reconnecting:

1. On first disconnect, reconnect after **1 second**.
2. Double the interval on each subsequent failure (2 s, 4 s, 8 s…) up to a maximum of **30 seconds**.
3. Pass `replay=<N>` on reconnect so you don't miss events that arrived while offline.

## Retention

All sync status data is held in Redis with a 24-hour TTL. For long-term audit, subscribe to the corresponding [`sync.started` / `sync.completed` / `sync.failed`](/api-reference/guides/webhooks) outgoing webhooks, which are persisted by Svix.
